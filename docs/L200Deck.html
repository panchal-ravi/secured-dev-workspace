how it breaks

What makes coding agents different

01
Untrusted code runs itself. The agent pulls packages off the internet and executes them at machine speed, unvetted, beside your secrets. In a workspace it runs in a disposable container with no standing credential to steal.
disposable runtime
02
Nothing scopes which tools it calls. A prompt injection hidden in a file or an issue turns "read this" into "call every tool and dump the database." A project-admin publishes a virtual MCP server holding only that project's tools; everything else returns 403.
scoped MCP token
03
A standing secret for every tool and model. Database URLs, API tokens, a provider key in .env, all wired into the agent's environment and readable by it. Vault mints each one just-in-time to tmpfs; the workspace never holds the real database URI or provider key.
minted, not pasted
04
No cap, no allow-list, no record. Pointed at a model endpoint, the agent streams your source off-box with no spend limit and no log of what was sent. One gateway holds the provider key, enforces a per-project budget, and logs every prompt and response.
one gateway
05
Full privilege, no human in the loop. A stray rm -rf, or a compromised agent, runs as you and reaches whatever your machine can reach, leaving no attributable trail. Every session is brokered and bound to a named person.
brokered · named
06
Code and keys on the device. A full clone of proprietary source, plus the keys to reach it, on a fleet you may not manage. The repo and tools live in a central container; a lost device carries nothing.
no local clone

HashiCorp · an IBM Company
why a workspace
what a secured workspace gives an agent

Five things your machine can't give an agent.

01
Containment. A mistake stays in the box. A stray rm -rf, a malicious install script, or a prompt injection plays out inside a disposable workspace, never on your machine and never within reach of your standing secrets.
contained
02
Hardware isolation. Not just a shared-kernel container. Plain containers share the host kernel, so one kernel exploit escapes to everything on the box. For untrusted code, Nomad places the workspace on a microVM pool with its own guest kernel: an escape has a machine boundary to cross.
microvm wall
03
Ephemeral, not fragile. Persistent to work in, disposable to recover. /home/dev sits on a durable volume that survives the loss of the node itself. If a workspace is wedged, Nomad reschedules it and your volume re-attaches intact. The container is disposable; your work isn't.
durable volume
04
Right-sized compute. The right machine for what you're building. A standard node, a GPU node for CUDA, or a hardware-isolated microVM: picked as a template tile, scheduled by Nomad. Server-class compute runs remotely, so your machine needn't even stay online.
gpu · microvm
05
Environment scrubbing. The agent never inherits your keys. Run an agent locally and it inherits your whole shell: every exported API key, cloud profile and .env on disk. In the workspace it starts clean, and the only credentials present are minted just-in-time.
no inherited keys

pillar 02 · access  ·  the required negative-isolation test

Each developer reaches only their own workspace.

alice → alice's workspace
200 · session authorized. Alice's managed group, matched on /token/email, grants authorize-session on exactly her target.
Boundary injects a Vault-signed SSH cert and the workspace opens in the IDE. No key touches the machine.
vs
bob → alice's workspace
403 · denied. Bob's group holds no grant on Alice's target, so the broker refuses before any connection exists.
The grant is per-developer and per-target, decided against the SSO identity before a session exists, not a firewall rule someone can widen. The denial is part of the required test suite.
why identity-bound authorization, not a shared jump host?A shared host authorizes at the network edge and trusts everyone who lands on it. Here the decision is made against the SSO identity before a session exists, so "reach only your own workspace" is enforced by the system, not by convention.

HashiCorp · an IBM Company
pillar 03 · credentials  ·  with what · Vault mints all four

Four credentials, none of them standing.

01
SSH session certificate. sshd trusts only a per-project Vault CA; Boundary injects a fresh cert each session, stamped with your email as key_id.
~5-min ttl
02
GitHub App token. No PAT anywhere. Vault mints a short-lived App installation token (contents:write), rendered only to tmpfs and re-minted before it expires.
1-hour ttl
03
LLM model key. A per-project virtual key for the LLM gateway, carrying an allow-list, a budget and a rate limit; the real provider key stays inside the gateway.
allow-list
04
MCP tool token. A per-project scoped token resolving to one virtual MCP server: the exact tools a project-admin exposed, and no database URI.
one server only
why short-lived certificates, not managed SSH keys?A key is a standing secret: it exists on disk somewhere, can be copied, and must be rotated and revoked. A per-session certificate is minted at connect time, expires on its own, is never stored, and its key_id ties every session to a named person. There is nothing to steal between sessions.

pillar 04 · runtime  ·  where does it run · Nomad

Same image — only the wall changes.

tier 1 · default

Container

A managed container on the standard pool with a persistent /home/dev volume, using shared-kernel Linux namespaces. The baseline for standard work.

isolation → namespaces
tier 2 · gpu

GPU node

The same image pinned to a g4dn.xlarge NVIDIA-T4 node for CUDA and heavier work, with an identical identity and credential stack.

proof → nvidia-smi sees the T4
tier 3 · microvm

Kata microVM

The same image inside a Kata microVM: its own guest kernel behind a KVM wall, on a bare-metal pool, for untrusted or high-risk code.

proof → uname -r, distinct kernel
why not microVMs for everything?Kata needs bare-metal nodes (KVM is unavailable under nested virtualization) and costs more per hour, so it stays opt-in for untrusted code rather than the default. Proof inside the box: uname -r shows a Kata guest kernel distinct from the host's, and /home/dev mounts over virtiofs. Making it the default is on the roadmap.
