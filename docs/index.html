A Level-300 Architecture Guide for Technical Audiences

Give your coding agents a secured workspace — not the keys to your machine.

Securing an AI agent has two fronts: the environment where it writes and tests code, and the platform where those workloads later run in production. The first is where the risk starts — and it's the architecture this page lays out. A coding agent runs with your full privileges: it reads your config files and secrets, pulls untrusted packages off the internet, and needs a credential for every MCP server and model it calls. On the developer's machine that means credential sprawl and an unbounded blast radius. So the agent — and the code, tools, and secrets it touches — moves into a central, network-isolated secured workspace that the developer opens straight from their everyday IDE — VS Code, or any editor with remote-development support — over a brokered SSH session. The editor stays local; the code, the agent, and every credential run remotely. A mistake, a malicious dependency, or a prompt injection stays contained, and nothing long-lived ever lands on the developer's machine. This guide walks the architecture from first principles, using standards you already run: OIDC single sign-on and the HashiCorp stack.

Vault is the credential authority behind both paths: it signs the short-lived SSH cert for the brokered session and issues the GitHub, LLM-gateway, and MCP-gateway credentials the agent uses inside the workspace, delivered by workload-identity federation. The identity provider and the workspace scheduler are swappable: any OIDC IdP in Verify's place, Nomad or Kubernetes in the scheduler's.

The whole chain. IBM Verify (or any OIDC IdP) confirms who you are. Boundary decides whether you may connect and brokers the session. Vault mints every short-lived credential — the session's SSH certificate plus the workspace's GitHub, LLM, and MCP keys. And Nomad (or Kubernetes) runs the workspace the agent works in.
01 · IDENTITY

Who are you?

Every session — and every action the agent takes on your behalf — is bound to a named person via your existing SSO. Never a shared account or a server address.

02 · ACCESS

May you connect?

An identity-aware broker is the only door in — no public address, SSH unreachable off-box. Each developer reaches only their own workspace (another's is denied — we test it), and the agent inside is never exposed to the network.

03 · CREDENTIAL

With what?

The agent holds nothing long-lived. Every credential — SSH certificate, git-push token, model key, scoped tool token — is minted just-in-time to in-memory tmpfs and scoped to the work, never a standing key on your machine. A per-project namespace keeps one project's secrets from ever reaching another.

04 · RUNTIME

Where does it run?

In a scheduled, isolated workspace, right-sized to the work — a GPU node for model development, or a microVM with its own kernel for untrusted code. Autonomous execution is contained there, never on your machine; a corrupted workspace is thrown away and rebuilt from a clean template, while your work on its durable volume survives a node failure.

05 · AI EGRESS

What can it reach?

Only what a project-admin allows. MCP tools, data, and models are reached through central gateways whose keys the agent never holds — every other tool returns 403, model use runs on a per-project budget and allow-list, and every prompt and response is logged.

Chapter 01 · Problem

The problem starts on the developer's machine

Remote developer workspaces are not new, and getting a developer's code and secrets off the machine is worth doing. But they were built for a person working carefully at the keyboard. An autonomous coding agent is a different problem: it acts unattended, at machine speed, with your full privilege, steered by untrusted input — the files, issues, and pages it reads — and it needs a credential, a tool, and a model for almost everything it does. The damage lands while the code is being written — an instruction it reads, a secret it hardcodes, a dependency it installs — before anything is ever committed or deployed. On an ungoverned machine no one decides what it may reach or spend, and nothing records what it did. Six pressures converge on that agent — each retired by one of the pillars, and by a project-admin who governs what the project's agents may touch.

Autonomous execution

Untrusted code runs itself

A coding agent installs and runs packages off the internet on its own, at machine speed — a malicious install script executes right next to your secrets and production access, with no human pausing to vet it. A generic remote workspace only relocates that blast; it doesn't contain it.

Retired by

runtime Untrusted code runs in a disposable container — or behind a hardware-virtualization wall — with no standing credentials to steal and nothing on the host to reach.

Ungoverned tools

Unbounded reach to tools & data

An agent reaches systems through MCP servers. With nothing scoping which servers, tools, or datasets it may call, a single prompt injection — instructions hidden in a file, an issue, or a page it reads — turns "read this" into "call every tool and exfiltrate the database." Nobody has decided what this project's agent is allowed to touch.

Retired by

AI egress A project-admin composes a virtual MCP server exposing only the tools that project needs; the workspace holds a scoped token that returns 200 on that server and 403 on every other tool and server.

Credential sprawl

A secret for every tool & model

Every MCP server and model the agent calls needs a credential — database URLs, API tokens, a provider key in .env. Wire them into the agent's environment and you have multiplied standing, long-lived secrets far beyond anything a human developer held — all readable by the agent, or by anyone who lands on the machine.

Retired by

credential Nothing is pasted anywhere. Vault mints each credential just-in-time to in-memory tmpfs; the workspace holds a scoped MCP token and a per-project LLM key — never the real database URI or provider key — and a per-project Vault namespace stops any of them crossing projects.

Ungoverned LLM

Model access with no budget or record

Pointed at a model endpoint, the agent streams your source and context off-box with no cap on spend, no limit on which models, and no record of what was sent. An agent looping unattended can burn budget or leak IP — and no one can answer "what did it send, and what did this project cost?"

Retired by

AI egress Every workspace's model traffic goes through one central gateway that holds the single provider key, enforces a per-project spend cap and rate limit, restricts models to an allow-list (403 outside it), and logs every prompt and response tagged to the project.

Blast radius

Runs unattended, at your privilege

An agent mistake — a stray rm -rf — or a compromised agent runs with your full privilege and no human in the loop to catch it: destructive commands, lateral reach across whatever the machine can touch. Regulators then demand an attributable, exportable trail an ungoverned device can't produce.

Retired by

runtime access identity The agent is boxed in an isolated per-project workspace, every session is bound to a named person and brokered, and each project is walled off by construction.

Endpoint exposure

Code & keys on the machine

Beneath all of it, the baseline: a full clone of proprietary source, plus the keys to reach it, sit on a sprawling, often-unmanaged fleet of devices. One lost or compromised machine walks the whole codebase out — the floor a remote workspace is expected to raise, and the ground everything above stands on.

Retired by

runtime The repo and tools live in a central container; the developer's machine holds no clone and no key. A lost device carries nothing.

The shape of the problem. None of these are fixed by moving the agent to a generic remote box — that just relocates an ungoverned agent. They share one root cause: a high-privilege agent acting on its own, holding the code and the secrets and reaching whatever tools and models it likes, with no one governing the scope, the spend, or the record. The answer is one place that governs it — a secured workspace where the tools it may call are scoped by a project-admin, its model access is centrally budgeted and logged, and identity, access, credentials, and isolation wrap around it.
Chapter 02 · Why a workspace

Why a coding agent needs a secured workspace

An AI coding agent shouldn't run on your machine at all — it should have a secured workspace of its own: a container Nomad schedules onto the right class of hardware, wraps in identity, credentials, and isolation, and can tear down and rebuild on demand. And it's not only safer — a workspace gives an autonomous agent five things your machine can't, each one covered in a chapter below.

Containment

A mistake stays in the box

An agent's stray rm -rf, a malicious install script, or a prompt injection plays out inside a disposable, Nomad-scheduled workspace — never on your machine, and never within reach of your code or standing secrets. When the work ends the workspace is torn down, and nothing the agent touched persists on your device.

Hardware isolation

Not just a shared-kernel container

Plain containers share the host kernel — one kernel exploit escapes to everything on the box. When an agent runs untrusted or high-risk code, Nomad can place its workspace on a microVM node pool, where it runs as a hardware-isolated VM with its own guest kernel — so an escape has a machine boundary to cross, not just a namespace.

→ Ch 06 · Runtime
Ephemeral, not fragile

Persistent to work in, disposable to recover

Your dependencies, tools, and working state live on a durable per-workspace volume that survives not just the session but the loss of the node itself — if a workspace is corrupted, wedged, or its node fails, Nomad reschedules it and your /home/dev re-attaches intact. The container is disposable and rebuilt from a clean template; the working data you care about is not.

→ Ch 06 · Runtime
Right-sized compute

The right machine for what you're building

The developer selects the workspace template the work calls for, and Nomad schedules it onto the matching node pool: a GPU node for CUDA and other GPU-accelerated work; a hardware-isolated microVM when the agent executes untrusted or security-sensitive code; a standard node for everyday app and service builds. Server-class compute runs remotely, so your machine stays free — and needn't even stay online while a long job runs.

→ Ch 06 · Runtime
Environment scrubbing

The agent never inherits your keys

Run an agent on your own machine and it inherits your whole shell — every exported API key, cloud profile, and .env on disk. In the workspace it starts from a clean environment; the only credentials present are minted just-in-time to in-memory tmpfs, scoped to the session, and gone when it ends.

Chapter 03 · Foundations

Foundations this stands on

Every product here is off-the-shelf — IBM Verify plus the HashiCorp stack. The value isn't the parts; it's wiring them together so each does one job. And nothing's locked in: the secured workspaces run on Kubernetes just as well as Nomad, and with any OIDC-compatible identity provider in place of Verify.

Identity · Verify

IBM Verify

Developers sign in with the company SSO they already use — no new account, no extra password. Both Boundary and Nomad trust that identity, so every workspace session and every action the agent takes is tied to a named person through the /token/email claim.

Why not per-vendor — is this IBM-only?

No. The design relies only on standard OIDC claims, not a specific vendor. Any OIDC-compliant IdP can stand in Verify's place where one is already in use.

Access · Boundary

HashiCorp Boundary

Gives each developer identity-aware access to their own secured workspace — which runs on Nomad in a private network with no public address. Boundary authorizes the person, brokers the session through its worker proxy, and injects the SSH credential, so the developer connects without ever handling a host address or a key.

Why brokered, not a bastion host?

A bastion is still a reachable host with standing keys and a shared surface. Boundary exposes no workspace to the network at all: the sshd is unreachable off-box, and the developer never learns a host address or holds a key.

Credentials · Vault

HashiCorp Vault

Hands the workspace every credential it needs, freshly minted and short-lived — the session SSH certificate, a git-push token, and the scoped tokens the agent uses to reach its MCP servers and LLM models. Nothing long-lived lands on the machine, and each project's secrets stay sealed in its own namespace.

Why per-project namespaces, not path prefixes?

A per-project Vault Enterprise namespace makes isolation Vault-enforced — a token minted in one namespace resolves only that namespace's paths. Path prefixes in a single namespace are the lighter, non-Enterprise alternative, but lean on policy correctness for the boundary.

Runtime · Nomad

HashiCorp Nomad

Runs the developer's workspace — and the coding agent inside it — as a managed, isolated container with a durable per-workspace volume that survives node failure, placed on the node pool the chosen template calls for: standard, GPU, or hardware-isolated microVM. Projects are walled off from one another by namespace, and a broken workspace is rescheduled onto a healthy node from a clean template — with its /home/dev re-attached — in seconds.

Why not require Kubernetes?

The same model — namespaces, scheduled pods, persistent volumes — maps directly onto Kubernetes wherever that is the house scheduler. The design needs only a scheduler with namespaces, not a specific one.

AI egress · Gateways

MCP + LLM gateways

Decide what the coding agent is allowed to reach. ContextForge scopes which MCP tools and data it can call; LiteLLM controls which LLM models it may use, enforces a per-project budget, and records every prompt and response — all without the workspace ever holding a real provider key.

Why centralize, not configure per workspace?

Point-to-point integrations scatter provider keys and data grants across every workspace. One gateway is a single policy-and-audit point: scope, budget, and a full prompt/response record — and the provider is swappable by one config line.

Principle

Standards, not a rebuild

You don't rip out what you already run. Two of the pieces are pluggable — the scheduler and the identity provider — so Nomad can give way to Kubernetes for the secured workspaces, and Verify to any OIDC-compatible IdP. The platform drops into a stack a team already operates.

Each product answers one question. Verify proves who you are. Boundary decides whether you may connect, and brokers the session. Vault issues every credential and keeps it short-lived. Nomad runs the workspace in isolation. The two AI gateways govern what the agent can reach. The chapters that follow take them one at a time.
Chapter 04 · Access

A single identity-aware door — no other way in

The simplest guarantee first: the secured workspace has no public address. The only way in is Boundary, which verifies each developer's SSO identity before any connection exists, brokers the session, and grants reach to only their own workspace on Nomad. The developer opens that workspace right inside their local IDE — VS Code, or any editor with remote-development support — through the brokered session, with the code and the agent running remotely. The agent inside is never exposed to the network — nothing off-box can dial it.

Each developer reaches only their own workspace — try it

Why identity-bound authorization, not a shared jump host?

A shared host authorizes at the network edge and trusts everyone who lands on it. Here the grant is per-developer and per-target: the decision is made against the SSO identity before a session exists, so "reach only your own workspace" is structural, not a firewall rule someone can widen.

Chapter 05 · Credentials

Nothing long-lived is ever handed out

You're in — and this is the part that makes it safe to hand a coding agent real privileges. Run that agent on your own machine and it inherits your whole shell: every exported API key, cloud profile, and .env on disk. In the workspace it starts from a clean environment and holds nothing standing. Whatever it needs next — to push a commit, call a model, or reach a tool — Vault mints on demand, renders it to in-memory tmpfs, and scopes it to the project's own Vault namespace. Four credentials, one trust fabric, and not one of them is a key left lying on the machine.

SSH

Session certificate

The workspace's sshd trusts only a per-project Vault SSH CA — static keys are inert (AuthorizedKeysFile none). Boundary injects a fresh certificate for each session, stamped with the developer's email as key_id for audit; a reconnect mints a new one. There is no key to steal, leak, or rotate.

Git

GitHub App token

Pushing needs no stored PAT — there is none anywhere. Vault's external GitHub plugin mints a short-lived App installation token from a pre-scoped, per-project contents:write permission set, rendered only to tmpfs and re-minted before its one-hour life runs out. Commits are the developer's; the push carries the project's App.

Model

LLM model key

The agent never holds a real model-provider key. Vault hands the workspace a per-project virtual key for the LLM gateway — scoped to an allow-list of models, a budget, and a rate limit — while the one real provider key stays inside the gateway. Ask for a model outside the list and it returns 403.

Tool

MCP tool token

To reach its tools the agent gets a per-project scoped token that resolves to a single virtual MCP server — the exact subset of tools a project-admin exposed. It answers 200 there and 403 on every other tool and server, and it carries no database URI: the agent never talks to a datastore directly.

Trust

Namespace + workload identity

None of these ride on a static Vault token, and none can reach across projects. Each project lives in its own Vault namespace, and Nomad trades a per-job workload identity for a short, read-only token — about thirty minutes, a handful of narrow read paths. One project's SSH CA, App token, model key, and tool token are unreachable from another's.

Why short-lived certificates, not managed SSH keys?

A key — however well managed — is a standing secret: it exists on disk somewhere, can be copied, and must be rotated and revoked. A per-session certificate has none of those properties: it is minted at connect time, expires on its own, is never stored, and its key_id ties every session to a named person for audit. There is simply nothing to steal between sessions.

Chapter 06 · Runtime

Isolated by construction, at two levels

An autonomous coding agent installs and runs untrusted code at machine speed — so where it runs decides how far a bad outcome can travel. Nomad contains it in two dimensions: tenants are walled off structurally, so one project can never reach another; and runtime isolation scales from a shared-kernel container up to a hardware-virtualization boundary for the riskiest code — the same image throughout, only the wall changes.

For a developer, choosing a stronger tier is just picking a different template tile in the Portal's Create workspace screen — nothing to configure. Behind that tile the OCI image and the entire credential stack are reused byte-for-byte; only the runtime boundary changes.

Tenant isolation is structural — remove a wall to see it

Each project gets its own Vault namespace, Boundary scope, and Nomad namespace. Cross-project access is impossible by construction, not policy-gated. Toggle a boundary off to read what it was preventing:

Per-project isolation boundaries

All boundaries engaged — cross-project access is structurally impossible.

  • Vault namespace removed: credentials would no longer resolve to only one project — a token minted for project A could reach project B's SSH CA, database role, and secrets. The hard isolation boundary is gone.
  • Boundary scope removed: brokered access is no longer partitioned per project — role grants could authorize sessions across project boundaries instead of within one.
  • Nomad namespace removed: workloads could schedule into one another's space; a namespace-scoped ACL backstop no longer contains a job to its project.

The runtime tiers

Tier 1 · default

Container

A managed Docker container on the standard node pool with a persistent /home/dev volume. It shares the host kernel through Linux namespaces — the baseline for standard work.

isolation: namespaces
Tier 2 · gpu

GPU node

The same workspace pinned to a g4dn.xlarge NVIDIA-T4 node for heavier workloads. Proof inside: nvidia-smi sees the T4.

isolation: namespaces + GPU
Tier 3 · microvm

Kata microVM

The same image inside a Kata Containers microVM — its own guest kernel behind a KVM wall — on a bare-metal pool. A container escape is contained by the VM, not just Linux namespaces.

isolation: hardware (KVM)

Proof point (microVM gate): inside the workspace uname -r shows a Kata guest kernel (e.g. 6.1.62) — different from the host node's — and /home/dev mounts over virtiofs. A distinct guest kernel can only happen inside the microVM.

Match the machine to the work. Most workspaces run standard; CUDA and other GPU-accelerated work gets a GPU node; untrusted or agent-driven code that warrants a hard wall gets the microVM — a one-line flavor change, with the same image and the same credential stack throughout. And because the runtime is immutable and rebuilt from the template on every placement, a workspace an agent wedges — a broken toolchain, a poisoned dependency — is discarded and rescheduled from clean in seconds: the container is disposable and rebuilt clean, while your /home/dev lives on a durable per-workspace volume that survives node failure and re-attaches wherever the workspace reschedules.

Why hardware isolation only for some workspaces, not all?

Kata microVMs need bare-metal nodes (KVM is unavailable in nested-virt guests) and cost more per hour, so they are an opt-in flavor for untrusted or high-risk code rather than the default. Because the image and credential stack are identical across tiers, offering hardware isolation is a one-line flavor definition on the platform side — a project-admin publishes the microVM template and it appears as another tile in the developer's picker. Making the microVM the default is on the roadmap.

Chapter 07 · AI egress

What the coding agent is allowed to reach

Every workspace runs a coding agent — inside the container, never on the developer's machine. That agent is exactly where the "code leaving via AI" risk lives, so its reach is governed the same way access is: it touches tools, data, and models only through two central gateways that scope, budget, and audit every call.

The workspace holds only a scoped MCP token and a per-project LLM virtual key, both rendered to tmpfs. It never holds a database URI or the real provider key — the gateways do.

Two gateways, two policy points — click either to inspect

Tools & data

MCP gateway · ContextForge

Federates each project's MCP server as a per-project virtual server. The agent holds a client token scoped to its own virtual server and reaches that and nothing else — every other project's server and the gateway's admin API return 403. The tools and data it can touch are exactly the subset a project-admin exposed, and no more.

Models

LLM gateway · LiteLLM

Serves the API the agent speaks and holds the one central provider key. Each project gets a virtual key scoped to allowed models with a budget and rate limit; the workspace authenticates with it and never sees the real key. Every prompt/response is logged per project, and the provider is swappable (DeepSeek → watsonx.ai) by a one-line config change with no workspace edit.

Governed by default, enforced by the credential: the workspace ships already pointed at the gateway — the developer configures no endpoint, key, or model — and the real control is the token itself, not a config file. The workspace holds only a scoped virtual key, so a request for a model outside its allow-list returns 403 at the gateway, whatever agent or setting sent it.

Governance you can hand an auditor. Because every call runs through the gateways, the record is central. Each session and action ties to a named person — the SSH certificate's key_id is the developer's email. Model access runs on a per-project budget and rate limit (for example $50 and 120 requests/min), and every prompt and response is logged and tagged to the project, with spend exportable from the gateway. Ask for a model outside the allow-list and it returns 403.
Chapter 08 · Experience

What the developer actually does

The developer sees none of this. They sign in, create a workspace, open it in their IDE, and start coding — four steps. No Terraform to write, no token to paste, no server address to look up; the machinery from the earlier chapters runs on its own.

Sign in with your normal company SSO. No account to create, no key to generate.

Reference & getting started

Each product owns one part of the security model. Only the base platform is provisioned with Terraform; projects and workspaces are created from the Portal — each step run by a different role, so no one person ever holds every privilege at once.

Who owns what

ProductThe one property it ownsQuestion answered
IBM VerifyOIDC single sign-on; every access bound to the /token/email claim.who are you
BoundaryIdentity-aware access broker; the single authenticated entry point, per-target authorization.may you connect
VaultCredential authority: SSH CA, ephemeral git tokens, dynamic DB roles, per-project secrets.with what credential
NomadScheduler and isolation boundary; namespace per tenant, node pool per hardware tier.where does it run
ContextForge + LiteLLMCentral MCP and model egress; scope, budget, and audit for the in-workspace agent.what can it reach

Three tiers, three roles

Only the base platform is provisioned with Terraform. Everything above it — projects and their workspaces — is created from the Portal, never HCL. Each role holds only what its tier needs: the Platform Admin runs the one privileged apply and onboards projects, Project Admins configure their own project, and developers only ever create and reach their own workspace.

TierRoleWhat they set up
Platform · terraform/infraPlatform AdminProvisions the base platform with Terraform — Boundary, Nomad, Vault, and the LLM + MCP gateways. Then creates each new project from the Portal, and with it a fresh Boundary scope, Vault namespace, and Nomad namespace.
Project · PortalProject AdminConfigures the project's MCP servers and workspace templates — from the Portal.
Workspace · PortalDeveloperCreates and connects to their own workspace — from the Portal.
